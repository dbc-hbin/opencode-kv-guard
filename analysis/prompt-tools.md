# KV/prefix audit: system and tool construction

Scope: read-only source audit of OpenCode 1.19.4 (`148842ef7cb1bc34192b3fff57d0f9721ab9c801`) versus OMP (`6f3fbc94c567c0ac619c013dd15d718356eecba1`). `OC/` below means `opencode-1.19.4-source/`; `OMP/` means `oh-my-pi-comparison-source/`. No source edits, builds, tests, formatters, or production requests were performed. On-prem LiteLLM/vLLM and its chat template are unavailable. Prefix consequences below are conditional on how that template places system messages and tools, not a claim of the production cause.

## Material conclusions, ranked

1. **Confirmed construction difference: OC regenerates a large early system message every provider iteration; OMP separates a stable head, trailing project context, and append-only date/cwd reminders.** OC assembles provider/agent prompt, environment, instruction file/URL contents, MCP instructions, skills, and user system text into the initial system string. The date is day-only, not a per-request timestamp. A changed date, instruction response, reference, agent/model identity, or server instruction changes this system string before conversation history. OMP's source explicitly moves date/cwd volatility to user-context reminders and keeps directory-dependent material after static prompt blocks. Thus an unchanged OC request is not intrinsically unstable, but live changes have an earlier prefix position. Evidence: `OC/packages/opencode/src/session/prompt.ts:1247-1290`; `OC/packages/opencode/src/session/llm/request.ts:56-110`; `OC/packages/opencode/src/session/system.ts:28-50,70-107`; `OC/packages/opencode/src/session/instruction.ts:91-103,110-169`; `OMP/packages/coding-agent/src/system-prompt.ts:1037-1052`; `OMP/packages/coding-agent/src/sdk.ts:4447-4471`.

2. **Confirmed presentation difference, conditional risk: OC normally sends every visible connected MCP schema directly; OMP can keep discoverable tools behind `xd://` with compact catalogs/on-demand docs.** OC consumes live cached MCP definitions on every iteration and removes definitions/instructions when a connection closes; tools/list_changed replaces schemas. This can change the model's tool prefix even when conversation history only appends. OMP generally mounts discoverable tools if read/write transport is available and they are not pinned top-level. Its non-MCP mount changes use hidden notices without rebuilding the system head; its external descriptions are bounded and schemas can stay on-demand. However OMP is not immune: MCP route changes and MCP instructions enter its rebuild signature, direct tools still change native schemas, and an inline device policy can carry schemas in the system head. OC experimental codemode also has bounded discovery, so 'OC always sends all MCP schemas' is false. Evidence: `OC/packages/opencode/src/session/tools.ts:386-397,488-491`; `OC/packages/opencode/src/mcp/index.ts:442-470,615-624,666-689`; `OMP/packages/coding-agent/src/session/session-tools.ts:1280-1305,1633-1639,2416-2461`; `OMP/packages/coding-agent/src/tools/xdev.ts:51-87,249-257,336-378`.

3. **Confirmed lifetime difference, conditional benefit: OMP snapshots selected dynamic tool-description inputs and announces changes in conversation history; OC's definition hook reruns per tool per iteration.** OMP freezes exactly the skill hint, advertised eval preludes, and user-tagged model-agent list at base-prompt rebuilds; eval-prelude and model-agent changes alone do not rebuild the prompt. OC reruns `tool.definition` for each built-in/custom tool and then adds its own task/codemode catalog. A plugin that adds time, counters, live filesystem state, or variable text therefore rewrites tool definitions on every request. There is no built-in OC definition-hook churn evidenced in the inspected default plugins; this is an installed-plugin/input risk, not an unconditional OC defect. Both applications permit arbitrary final prompt/payload modification by extensions. Evidence: `OC/packages/opencode/src/tool/registry.ts:310-338`; `OMP/packages/coding-agent/src/session/session-tools.ts:311-324,652-658,1382-1409,1783-1787,1830-1837`; `OMP/packages/coding-agent/src/extensibility/extensions/runner.ts:2186-2220,2254-2302`.

4. **Confirmed request-specific prefix mutation: OC JSON-output mode adds both a user-supplied `StructuredOutput` schema and an early system instruction.** Switching between text and schema output, or changing the requested schema, changes tool/system inputs independently of ordinary conversational append. This is intended behavior, not a cache bug. OMP is not categorically exempt: structured task/yield output and workpool state can change its schemas too. Evidence: `OC/packages/opencode/src/session/prompt.ts:1227-1234,1266-1290`; `OMP/packages/coding-agent/src/task/index.ts:712-725`; `OMP/packages/coding-agent/src/tools/yield.ts:382-397`.

5. **Confirmed per-agent/per-user catalog changes; not an OC-only pathology.** OC filters final tools using merged agent/session policy plus the latest user tool toggles. Agent changes also alter provider prompt, task listings, skills, edit/write versus apply_patch selection, and MCP-instruction visibility. OMP similarly changes selected tools, delegation/spawn catalogs, plan-mode task schema, edit dialect, and mounted/direct partition. These changes legitimately alter prefixes. Freezing permissions or continuing to advertise disabled capabilities is not a correct fix. Evidence: `OC/packages/opencode/src/session/llm/request.ts:210-215`; `OC/packages/opencode/src/session/prompt.ts:1053-1067`; `OC/packages/opencode/src/tool/registry.ts:266-307`; `OC/packages/opencode/src/session/system.ts:110-141`; `OMP/packages/coding-agent/src/task/index.ts:170-213,712-759`; `OMP/packages/coding-agent/src/session/session-tools.ts:1251-1305`.

6. **Low-confidence conditional surface, not established nondeterminism: instruction glob order is not canonicalized in OC.** `Instruction.systemPaths` stores glob matches in a Set and renders insertion order; `FSUtil.globUp` appends raw `Glob.scan` output and the adapter calls the `glob` package without sorting. A changed glob result order could reorder whole early instruction blocks. No varying result was observed or executed. Do not report this as proven random churn. OMP context-file sorting is by authority depth with stable ties, not a universal lexical canonicalization either. Evidence: `OC/packages/opencode/src/session/instruction.ts:110-168`; `OC/packages/core/src/fs-util.ts:146-151,182-196`; `OC/packages/core/src/util/glob.ts:23-29`; `OMP/packages/coding-agent/src/system-prompt.ts:323-341,379-386`.

The most defensible new investigation targets from this surface are **live MCP/schema changes, installed `tool.definition`/system-transform plugins, per-message tool/format changes, and live instruction fetches**. None was observed on the unavailable server. Static differences in schema size, tool vocabulary, or system prose do not by themselves explain a miss on every unchanged successive request.

## Important negatives and limits

- **No unsorted OC top-level tool list finding.** Final tools are alphabetically sorted (`session/llm/request.ts:181`). Task agent names, skills, references and MCP instructions are also sorted at rendering. This rules out the common claim that connection completion order alone scrambles all names.
- **No timestamp/random-ID in the inspected native tool definitions.** OC tool call IDs, execution timestamps, temporary truncation output names and attachments belong to results/history, not the static schema catalog. OC shell temp root is a stable global path, not a newly generated per-request filename (`tool/shell/prompt.ts:273-290`).
- **Normal permission approvals are not a reason to freeze policy.** OC's remembered approval array and OMP's execute-only ACP proxy do not by themselves change advertised schemas. Live denies/explicit toggles/agent changes must remain effective.
- **OMP append-only storage is not proof of identical requests.** It still normalizes live tool getters each request and accepts context/payload hooks. The implicit base-prompt freeze in `session/session-tools.ts:1588-1594` applies only when the model advertises `thinking.prefixBinding === true`; generic custom OpenAI-compatible models are not automatically covered. Direct tool schemas still follow the live selected catalog even when a bound system head is retained (`1433-1475`).
- **A path/platform/model name changing between sessions is a cross-session sharing limitation, not necessarily a within-session hit failure.** Both applications include platform and model information. OMP merely delays directory-dependent material until after its static head; actual token ordering around tools is the deployment chat template's responsibility.
- **Schema transformations and property annotations change size/shape, not time.** Strict flags, `additionalProperties`, injected `i`, examples, native-vs-inline descriptors and schema dialects are token-affecting where the server template renders them, but deterministic fixed inputs remain reusable.
- **Headers and sampling settings alone are not token-prefix text.** OC `chat.headers` and ordinary temperature/topP/max-output changes do not directly edit messages or schemas. Provider options that alter template behavior or routing need the transport/template audit; this report does not infer them from header bytes.
- The exact serialized LiteLLM-to-vLLM prompt, template tool placement, cache statistics, node affinity, real installed hooks, tool toggles, and live MCP/instruction changes were not observed. Those observations are required to attribute an actual miss.

## Plugin-fixability

**Safe plugin work within exposed OC hooks:** remove plugin-owned volatile generated text; canonicalize the plugin's own dictionaries/schemas; make plugin content deterministic for the same live inputs; place plugin-owned dynamic notices at the newest conversation turn instead of rewriting old/system text. A system transform can split/reposition generated environment/date content because it sees final assembled system text, but it must preserve current user/agent/system policy and semantic ordering. Stabilizing a cache key is separate from stabilizing prompt tokens.

**Only partial through `tool.definition`:** it can rewrite built-in/custom description and parameters, but receives only `toolID`; it does not receive session/model/agent/policy. OC appends task/codemode descriptions after the hook. Direct MCP entries are added in `session/tools.ts`, bypassing the registry definition hook. Therefore this hook cannot safely freeze or fully normalize the final per-session catalog, and it cannot alone repair direct MCP schema churn. Evidence: `tool/registry.ts:310-338`; `session/tools.ts:390-397`; `packages/plugin/src/index.ts:332-334`.

**Needs core/final request interception or explicit configuration:** deterministic final MCP/schema presentation, preserving a stable authorization-correct catalog, moving true live instruction changes into append-only context with provenance, and native handling of date/cwd lifetimes. OC experimental codemode is an existing opt-in alternative to direct MCP schemas, but its catalog still reflects live MCP metadata. A custom provider/fetch layer could observe final request bodies, but no claim is made here that an ordinary system/tool-definition plugin receives such a hook.

**Do not 'fix' by memoizing the first system/tool list forever.** That can preserve stale user instructions, revoked permissions, disconnected tools or changed schemas. Snapshot only immutable or explicitly versioned presentation inputs; allow actual policy changes and announce them correctly. A new valid prompt prefix is expected when the user intentionally changes capability or output contracts.
