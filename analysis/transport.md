# OpenCode 1.19.4 versus OMP: transport, compatibility, and KV pressure audit

## Scope and evidence boundary

Read-only source comparison of OC `opencode-1.19.4-source` at the assignment's pin `148842ef7cb1bc34192b3fff57d0f9721ab9c801`, and OMP `oh-my-pi-comparison-source` at `6f3fbc94c567c0ac619c013dd15d718356eecba1`. `OC:` and `OMP:` references below are relative to these roots. No project files were edited; no builds, tests, formatters, inference requests, or on-prem probes were run. The report itself is the requested local artifact.

The on-prem LiteLLM configuration, vLLM version, model/chat template, request bodies, replica placement, and cache counters were unavailable. Confirmed source differences are not a confirmed production explanation. In particular, distinguish:

1. **Token-prefix identity:** messages, replayed thinking, tools, and template flags that can change the actual token sequence.
2. **Routing/cache namespace:** model ID, replica selection, and cache keys, which can change the cache population available for an identical prefix.
3. **Capacity/pressure:** simultaneous calls, output reservations, timeouts, and retries. These can increase prefill or KV eviction without changing the prefix.
4. **Reporting only:** a client displaying zero cached tokens does not prove vLLM missed its cache.

## Principal findings

### T1. Conditional high: OMP has explicit Qwen history-template preservation; generic OC compatible transport does not add it

**Confirmed difference.** OMP detects local OpenAI-compatible backends and sets `replayReasoningContent` and `qwenPreserveThinking`; its request encoder emits `chat_template_kwargs.preserve_thinking=true` before any reasoning-enabled/disabled early return. With the `qwen` dialect it also emits top-level `preserve_thinking=true`. The vLLM provider selects the `qwen-chat-template` dialect, so its control is in template kwargs, rather than relying on a top-level thinking flag.

Evidence:
- `OMP:packages/catalog/src/compat/resolve.ts:268-299,346-384`: local providers include `llama.cpp`, `lm-studio`, `vllm`, and `ollama`; custom loopback/private-IP/`.local` URLs also count. Backend identity is `providerType ?? provider`.
- `OMP:packages/catalog/src/compat/resolve.ts:540-565,588-617`: replay/preservation flags, local grammar normalization, local first-event timeout, and generic cache-key baseline.
- `OMP:packages/catalog/src/compat/rules/providers/vllm.kdl:3-12`: Qwen uses `qwen-chat-template`.
- `OMP:packages/catalog/src/compat/rules/classes/qwen.kdl:36-64`: vLLM Qwen >=3.8 template-effort policy.
- `OMP:packages/ai/src/providers/openai-shared.ts:1154-1197,1220-1256`: preservation and template kwargs emission.
- `OC:packages/opencode/src/provider/transform.ts:1220-1338`: automatic thinking controls are provider/model-specific (`baseten`, selected `opencode`, zai/zhipu, alibaba-cn); there is no generic local-Qwen preservation injection in this options path.

**Critical qualification:** OMP explicitly excludes a declared `litellm` backend from `isLocalOpenAICompatBackend`, even on a private URL (`resolve.ts:276,366-368`). Consequently, a properly declared custom provider with `providerType: litellm` does **not** automatically obtain Qwen thinking preservation or generic local reasoning replay from this heuristic. A custom provider pointing at a private LiteLLM IP, but not declared as LiteLLM, can obtain it. A public/internal DNS name without `.local` is not recognized merely because it resolves privately. This is a conditional advantage, not an OMP-wide fix for every custom -> LiteLLM -> vLLM route.

**Counterexample to an overbroad diagnosis:** OC's compatible SDK already serializes ordinary nonempty reasoning parts as `reasoning_content`; it does not universally drop them on arbitrary custom domains. `OC:packages/opencode/src/provider/transform.ts:303-348` also fills DeepSeek/interleaved reasoning fields. Pinned SDK converter original-source lines 171-174 and 203-208 collect and emit reasoning. Losing historical thinking in the **server template** is a different issue from failing to send the `reasoning_content` field.

**Consequence [INFERENCE]:** if the served template strips older thinking by default, a previously generated `<think>` segment can disappear from a later rendered prompt even when the client resends its reasoning. Cache reuse then stops at that first altered historical segment. This needs the real template and rendered-token comparison to establish.

**Fixability:** backend/model-specific request configuration or a targeted `chat.params` plugin can supply the accepted `chat_template_kwargs` contract; native OC local/model policy could automate it. Do not force this flag for every model or freeze a user's reasoning selection. Keep the history-preservation knob separate from the current-turn thinking knob.

### T2. Conditional high/medium: compatible SDK field translation is selective, and OC mode expansion can camel-case fields the SDK does not translate back

**Confirmed wire contract.** OC merges default options, model options, agent options, then the selected user variant (`OC:packages/opencode/src/session/llm/request.ts:80-93`). These are wrapped under the SDK's provider namespace (`OC:packages/opencode/src/provider/transform.ts:1462-1478`). In compatible SDK 2.0.41:

- `reasoningEffort` becomes `reasoning_effort`; `textVerbosity` becomes `verbosity`.
- Standard `maxOutputTokens` becomes `max_tokens`.
- Unknown provider-namespace keys are copied to the top-level body **unchanged**.
- The unknown-key spread occurs after `model` and `max_tokens`, but before final `reasoning_effort`, `verbosity`, `messages`, `tools`, and `tool_choice` assignments.

Evidence: pinned SDK `src/chat/openai-compatible-chat-language-model.ts:198-252`, especially `model:202`, `max_tokens:208`, unknown-key spread `231-240`, and mapped reasoning `243-244`. Its recognized option schema is only `user`, `reasoningEffort`, `textVerbosity`, and `strictJsonSchema` (`src/chat/openai-compatible-chat-options.ts:5-30`).

This means:
- `chat_template_kwargs`, `enable_thinking`, `thinking`, `preserve_thinking`, and raw `prompt_cache_key` can survive when supplied as correctly spelled unknown wire keys.
- `promptCacheKey` is not translated; it is emitted as camelCase if supplied. OC's optional `setCacheKey:true` branch generates exactly that spelling (`transform.ts:1323-1335`). This corroborates the established cache-key issue; it is conditional on enabling that option, not the default compatible body.
- Raw `reasoning_effort` in model/agent options is copied and then overwritten by the mapped `compatibleOptions.reasoningEffort`, which may be undefined. Use the SDK's recognized `reasoningEffort` for this field. Likewise, arbitrary `tool_choice`/`tools`/`messages` options cannot override the later SDK-owned assignments.
- A raw `max_tokens` option can override the standard output cap, while raw `max_completion_tokens` can coexist with the SDK's generated `max_tokens`. An arbitrary raw `model` can override the wire ID even though OC's transforms remain keyed to its configured model. These are explicit misconfiguration possibilities, not spontaneous per-turn changes.

**Additional confirmed conditional defect:** OC models.dev experimental mode expansion runs **every top-level snake_case key** through snake-to-camel conversion (`OC:packages/opencode/src/provider/provider.ts:1374-1408`). This works for recognized `reasoning_effort`, but would turn a mode body `chat_template_kwargs` into `chatTemplateKwargs`, `enable_thinking` into `enableThinking`, or `prompt_cache_key` into `promptCacheKey`; compatible SDK 2.0.41 does not convert those unknown keys back. This mode path is distinct from ordinary user-authored model `options`, which are not universally camel-cased. It matters only if an actual selected experimental mode contains such fields; no production mode selection is known.

**OMP comparison:** OMP shapes `max_tokens`/`max_completion_tokens`, template kwargs, and reasoning wire controls explicitly (`OMP:packages/ai/src/providers/openai-completions.ts:2216-2254`; `openai-shared.ts:1154-1282`) and applies `compat.extraBody` near the end. It does not use this SDK's generic unknown-key spelling convention.

**Fixability:** use documented camelCase only for SDK-recognized fields and exact wire spelling for unknown extras; correct native mode translation by a field-aware map, not universal camelization. A payload plugin can fix a known selected mode. Stable wrong flags can cause persistent template mismatch/ignored thinking controls, but are not evidence of random prefix churn by themselves.

### T3. Conditional high for very slow prefill: OC retains a 300-second header deadline where OMP disables it for recognized local-serving URLs

**Confirmed difference:** OC defaults both `headerTimeout` and `chunkTimeout` to 300,000 ms (`OC:packages/opencode/src/provider/provider.ts:94-125`). It arms a header abort controller and clears it when fetch settles, so it is correctly a pre-response deadline, not an accidental five-minute total-stream deadline. `timeout`, when explicitly set, is separately absolute. `timeout:false` is passed to Bun fetch in both clients, so there is no additional default Bun five-minute fetch timer in these audited paths.

OMP derives `streamFirstEventTimeoutMs:0` for `isLocalServingBackend` (`OMP:packages/catalog/src/compat/resolve.ts:383,592`). The latter includes a private URL even when declared as LiteLLM and excluded from local template replay. Its helper preserves the zero sentinel (`OMP:packages/ai/src/utils/idle-iterator.ts:71-96`). The provider arms no positive pre-header watchdog in that case (`OMP:packages/ai/src/providers/openai-completions.ts:856-864,932-940`). Generic nonlocal endpoints otherwise default to a similar 300-second first-event and idle budget (`idle-iterator.ts:5-6,40-96`).

**Consequence [INFERENCE]:** a cold/large prefill or proxy queue exceeding 300 seconds before headers can be aborted and redone by OC while OMP waits. That looks like repeated prefill or poor throughput, not a changed token prefix. It requires actual timings. With ordinary prompt latency below five minutes, this difference is irrelevant.

**Shared/countervailing behavior:** both default to a five-minute streaming-idle budget. OC resets at each raw body read (`provider.ts:37-79`); OMP's iterator supports semantic progress rather than keepalive-only progress (`idle-iterator.ts:131-140` and provider usage). Thus keepalive-only stalls can be tolerated longer by OC, not OMP. Cancellation on either client cannot prove that the proxy successfully stopped upstream vLLM work.

**Fixability:** measured provider-specific OC `headerTimeout` tuning (including `false` when appropriate) without removing stream-idle protection; no project rewrite needed.

### T4. Conditional medium: OC title generation is an early unrelated-prefix call, with the main output budget, while OMP's default fork preserves the live prefix and bounds elapsed time

**OC confirmed:** on the first loop step OC forks title generation in parallel (`OC:packages/opencode/src/session/prompt.ts:1132-1139`). It selects the title agent's model, otherwise a small model, otherwise the main model; it sends title-agent system content, no tools, a title-request prefix, `small:true`, the **same session ID**, and `retries:2` (`prompt.ts:193-236`). It only runs for a root session still using the default title and one real user turn. `getSmallModel` can return undefined for a custom provider with no recognized small family (`provider.ts:1964-2030`).

`small:true` changes provider options, not the max-output budget: request preparation still calculates `ProviderTransform.maxOutputTokens` (`request.ts:80-93,118-130`). `smallOptions` uses the first configured variant (`transform.ts:1390-1412`); for a generic reasoning-compatible model this is often low effort, **not** explicit reasoning disable. The output ceiling remains `min(model.limit.output, 32,000) || 32,000` absent an override (`transform.ts:18,1481-1483`). The title small path also bypasses the normal auto-generated `setCacheKey` option branch; it does not automatically inherit the normal turn's generated `promptCacheKey`.

**OMP confirmed counterexample to 'only OC runs parallel titles':** OMP also runs background titles. Its `fork` path calls `runEphemeralTurn` on the current model and snapshot with a 15-second timeout (`OMP:packages/coding-agent/src/session/agent-session.ts:495,10717-10771`). The side turn uses the existing system/tools/history, a distinct provider conversation ID, and the parent prompt-cache key (`agent-session.ts:12599-12680`). If it falls back to a separate tiny-title model, that path has a 1,024-token cap and `disableReasoning:true`, `temperature:0` (`utils/title-generator.ts:132-142,355-395`), and a stable separate title session ID (`agent-session.ts:10916-10964`). It can still use the current model through title fallback selection (`title-generator.ts:156-179`).

**Consequence [INFERENCE]:** OC's title call can introduce a short unrelated early prefix on the same deployment and affinity identity while the main request prefills, especially with no small model. That can compete for active KV/memory or a slot-based server's prompt buffer. vLLM APC is not a single conversation transcript selected by an arbitrary session header, so this does not establish that the title 'overwrites' its cache. OMP's fork also uses inference capacity and can warm a divergent suffix; it is not free.

**Fixability:** explicit title/small model, title-specific output cap via `chat.params`, or an explicit user-requested title disable. A small cap is an admission ceiling, not proof of actual generation duration. Do not claim that every 32k ceiling consumes 32k KV or 32k output tokens.

### T5. Conditional medium: OC's processor retries the whole stream after a retryable failure without the OMP provider wrapper's pre-output commit gate

**OC:** main `streamText` uses `maxRetries: input.retries ?? 0` (`OC:packages/opencode/src/session/llm.ts:315-324`), so the main request does **not** silently acquire AI SDK's default two retries. The title explicitly requests two. The processor then wraps the entire stream-drain in an outer retry policy (`processor.ts:642-690`). Its policy retries recognized API/network/timeout failures up to its configured maximum five retries, with 2-second exponential base, jitter, and Retry-After handling (`session/retry.ts:26-80,88-167,184-205`). There is no meaningful-output commit guard around that outer `Effect.retry` in the audited processor span; it resets current text/reasoning tracking and calls `llm.stream(streamInput)` again.

Pinned AI SDK 6.0.168 confirms default `maxRetries ?? 2`, but honors explicit zero (`src/util/prepare-retries.ts:38-45`; `src/util/retry-with-exponential-backoff.ts:99-111`). `stream-text.ts:1264-1267,1612` uses that prepared retry function for `doStream`. Compatible provider 2.0.41 itself just calls `postJsonToApi`; it does not hide an independent OpenAI SDK client retry loop.

**OMP:** it no longer uses the `openai` npm client in this path. Its own `postOpenAIStream` JSON-serializes once and defaults to six total HTTP attempts; transport retries resend the same bytes (`OMP:packages/ai/src/utils/openai-http.ts:1-33,66-76,102-128`). `max_parallel_requests` LiteLLM admission rejections bypass transport retry (`openai-http.ts:37-62,113-119`), unlike OC's generic 429 retry handling. A separate provider-stream wrapper permits one transient provider-error retry and up to two benign-empty retries **only before meaningful output commits** (`openai-completions.ts:1887-1892`; `utils/empty-completion-retry.ts:39-57,97-187`). Broader session recovery may have additional behavior; this is not a claim OMP can never recover after partial output.

**OMP counterexample:** OMP itself may make more transport attempts than OC's inner main call; empty-response handling and strict/reasoning negotiation also add calls. Its count is not always lower. OMP can retry with different flags after a recognized 400/422, then remember the negotiated result (`openai-completions.ts:985-1036`); that is a bounded compatibility transition, not per-request randomness.

**Consequence [INFERENCE]:** after a partial-stream failure OC may repeat expensive inference using the same input prefix. The input prefix can still hit APC; repeated decode and transient backend work can increase pressure. A 429 before model admission has no upstream KV workload to evict. Neither retry count nor a failed response establishes cache invalidation.

**Fixability:** targeted timeout/admission/replay policy and clear user-visible partial-output recovery. Do not suggest disabling all error recovery. A provider-level or session-aware implementation is preferable to a plugin blindly retrying requests again.

### T6. Confirmed cache/affinity differences, but cache keys and headers are not a token-preservation mechanism

**OC:** non-OpenCode requests already carry `x-opencode-session-id`, `x-session-affinity`, and `X-Session-Id`; children also carry parent-session headers, with model headers and `chat.headers` plugin output taking precedence (`OC:packages/opencode/src/session/llm/request.ts:181-202`). No finding here supports 'OC has no affinity'. The compatible SDK factory is stable/cached by provider/options and the language model by provider/logical model (`provider.ts:1800-1873,1921-1943`); no fresh per-turn UUID/cache salt is introduced by that factory.

**OMP:** LiteLLM wire policy explicitly uses `x-litellm-session-id` (`OMP:packages/catalog/src/compat/rules/providers/litellm.kdl:3-9`; `packages/ai/src/providers/inference-headers.ts:64-79`; `openai-shared.ts:350-363`). The rule's own stated purpose is grouping request logs into sessions; source does not prove this header enables replica affinity or vLLM APC. Correct behavior for custom aliases requires `providerType: litellm` or equivalent explicit compat. OMP separates conversation IDs from explicit prompt-cache IDs (`openai-shared.ts:172-199,350-363,545-556`).

**Important counterexample:** generic OMP compatible models default `supportsPromptCacheKey:false` (`catalog/src/compat/resolve.ts:617`), and the body emits `prompt_cache_key` only when that compat gate is true, or a supported prompt-cache breakpoint policy is active (`openai-completions.ts:2009-2042`). Thus 'OMP always sends a correct prompt_cache_key while OC sends none' is false. Neither client must send a prompt-cache key for a backend that keys APC by tokens; whether LiteLLM uses keys/headers for routing is server policy.

**Fixability:** exact header/body spelling and declared backend metadata are client/config fixable. Replica stickiness, routing based on that field, cache salt, block hashing, APC enablement, and memory capacity require backend evidence/configuration. Preserve actual child conversation identities while sharing an explicit cache affinity only where the backend contract supports that; do not reuse one mutable provider conversation for concurrent independent requests.

## Endpoint, alias, and SDK mapping

### Construction and endpoint selection

- OC new custom models default to `@ai-sdk/openai-compatible` if no explicit/inherited npm package applies (`OC:provider/provider.ts:1544-1555`). Compatible SDK `languageModel` returns a chat model, posting `/chat/completions` (`SDK compatible src/openai-compatible-provider.ts:156-164,182-186`; chat model `:378-384`). It forces streaming usage on unless provider `includeUsage:false` (`OC:provider.ts:1819-1821`; SDK chat `:365-372`). OMP generally also includes `stream_options.include_usage=true` unless compat disables it (`OMP:openai-completions.ts:2069-2071`). This flag is not token-prefix content.
- If OC is configured with `@ai-sdk/openai` instead, SDK 3.0.88's **default `languageModel` is Responses**, not Chat Completions (`SDK openai src/openai-provider.ts:219-245`). OC's built-in `openai` loader explicitly selects `.responses` too (`OC:provider.ts:242-249`). A change of npm package is therefore a change of endpoint and serialization contract, not a cosmetic alternative compatible provider. A server that implements only Chat Completions can fail on this choice. OMP separates API identity explicitly as `openai-completions` versus `openai-responses`.
- OC's experimental native runtime is opt-in (`llm.ts:254-294`) and refuses arbitrary custom provider IDs: only `openai`, `anthropic`, and `opencode*` are admitted (`llm/native-runtime.ts:52-73`). The ordinary custom provider path remains AI SDK even with the flag enabled. The native adapter therefore cannot be blamed for ordinary custom -> LiteLLM behavior without the actual provider ID/flag.
- Pin evidence: OC `package.json:67,164,168`, `bun.lock:585-586,1124`: `ai@6.0.168`, compatible `2.0.41`, OpenAI `3.0.88`. Compatible patch only preserves an error chunk's full object rather than just `.message` (`patches/@ai-sdk%2Fopenai-compatible@2.0.41.patch:1-43`); it does not alter prompt/template serialization. OpenAI patch changes service-tier support/gating; it is not a compatible-provider patch. OMP's audited completions module imports its own `postOpenAIStream`, wire types, and compat helpers (`packages/ai/src/providers/openai-completions.ts:1-95`), not the OpenAI npm SDK.

### Aliases, variants, and local detection

- OC separates logical config key `modelID` from wire `apiID = model.id ?? existingModel.api.id ?? modelID` (`provider.ts:1544-1567`). The wire model is `model.api.id` (`provider.ts:1928-1941`), while various transforms look at logical `model.id` or wire ID. Custom models without inherited metadata default `reasoning:false`, `temperature:false`, `context:0`, `output:0`; tool-call capability defaults true (`provider.ts:1572-1616`). DeepSeek-name auto-interleaving is one explicit exception (`:1596-1602`). A deployment alias hiding lineage does not magically inherit upstream capabilities.
- OC generic compatible reasoning variants are low/medium/high (plus special model exceptions), gated on `model.capabilities.reasoning` (`transform.ts:790-794,990-1002`). The chosen user variant merges last; small requests instead use the first variant (`llm/request.ts:80-93`; `transform.ts:1390-1412`). The initial default-options path does not set generic compatible reasoning effort to medium merely because the model supports reasoning; it does set medium for its explicit gpt-5-name branch (`transform.ts:1353-1384`).
- SDK compatible comments say reasoning/verbosity default to medium, but its actual schema is `.optional()`, without a Zod default, and request fields are assigned from those optional values (`SDK options:13-20`; chat model:243-244). Omitted fields are omitted by JSON serialization; backend defaults decide. Do not report the comment as an SDK-injected default.
- OMP can derive recognized identity from a `requestModelId` when a logical alias is unknown (`catalog/src/compat/resolve.ts:124-141`); provider rules resolve under `providerType ?? provider` (`:1311-1322`). Wire IDs resolve from effort routing, then `requestModelId`, then `id` (`catalog/src/model-thinking.ts:147-148`; `ai/src/providers/openai-completions.ts:395-407`). Effort-routing variants can really select a different wire model. That intentionally selects a different backend/cache namespace; it is not accidental nonce churn.
- With stable model, agent, user variant, compat, and plugins, the audited merges and constructors are deterministic. Switching models, effort-routed deployments, system persona, tool permissions, or a template-affecting variant can legitimately change tokens or cache namespace. Neither client guarantees prefix identity across such changes.
- Sampling fields (`temperature`, `top_p`, penalties), output limit, service tier, stream flags, and HTTP headers are not normally part of chat-template token input. They affect output, routing, admission, or cost. Reasoning/template flags **can** be template inputs; do not put all options into one 'cache key changed' bucket.

## Tools and response compatibility

- Compatible SDK 2.0.41 preserves supplied function name/description/schema; it only emits `strict` when explicitly present (`src/chat/openai-compatible-prepare-tools.ts:52-67`). An empty tools array becomes undefined, and with no tools it removes tool choice (`:33-40`); with tools but no choice it leaves choice undefined (`:71-72`). Provider-defined tools warn as unsupported (`:48-52`). It does not add a generic strict-true default.
- OC explicitly sets `strict:false` for OpenAI/azure/mantle SDK families, **not** its generic compatible family (`llm/request.ts:149-158`). Its `_noop` compatibility tool is Copilot-only (`:159-178`), not a hidden tool inserted into every custom provider request. Tool sorting is already present (`:184`). Do not diagnose unstable generic tool ordering or a universal no-op tool here.
- SDK structured-output schema strictness defaults true only for JSON schema response format; provider structured-output support itself defaults false (`SDK chat model:76-96,165-183,213-228`; factory passes `supportsStructuredOutputs`). OC's ordinary custom structured-output route uses a required tool (`session/prompt.ts:1272-1287`), not an automatic strict JSON-schema `response_format` in every request.
- OMP chooses tools, named/forced tool-choice compatibility, no-tools/history behavior, and reasoning suppression under tool choice in `openai-completions.ts:2111-2214`. It can emit `tools:[]` only for unspecified tools plus tool history, while explicit `[]` remains an opt-out. It drops redundant/inconsistent no-tools tool choice. These are compatibility behaviors, not proof its ordinary static schema creates a more reusable prefix.
- OMP strict-tools/reasoning fallback can change a later request's schema/flags once after an actual rejection (`openai-completions.ts:985-1036`). It caches the negotiation by provider-session scope, but explicit reasoning-disable fallback is request-local to avoid poisoning future thinking-enabled turns. This is a counterexample to 'OMP never changes flags'.
- Final compatible response parser and replay differences, including alternate reasoning fields, thinking signatures, and usage aliases, are covered by the sibling history audit. Transport-relevant conclusion corroborated here: ordinary nonempty OC reasoning replay is supported; template preservation is separate. OMP usage normalization is broader (`openai-completions.ts:2268-2331`). Missing cache accounting is not evidence of a server miss.
- Static differences between OC and OMP tool JSON can change the first request's tokens without breaking **each client's own** repeated prefix. Actual per-turn schema/description/permission changes are the reuse concern. Do not freeze live authorization or tool policy merely to keep tokens identical.

## Non-causes and counterexamples to retain in the final comparison

1. No generic timestamp, request UUID, random seed, or request salt is added to the compatible body by the audited OC constructor/getArgs path. Generated tool-call IDs belong to response normalization and are replayed later; they are not a new system-prompt nonce each turn.
2. Request top-level JSON ordering and HTTP header order are not normally the rendered token sequence. Tool schema JSON **may** be rendered by a template, but stable serialization differences between products do not explain one product losing its own previously cached prefix.
3. `stream_options.include_usage`, raw error-object patching, telemetry/user-agent/affinity headers, strict output grammar, and cache counter display should not be described as automatic prompt-token mutations.
4. Neither a session header nor `prompt_cache_key` guarantees a cache hit. Correct repeated tokens can still land on a different model/replica or face evicted blocks; a missing body cache key can coexist with working vLLM APC.
5. OC supports custom wire extras, ordinary reasoning replay, sorted tool names, stable provider construction, scoped abort, and explicit retry policy. Claims that it lacks all of these are contradicted by source.
6. OMP can disable pre-header timeouts for local serving, preserve Qwen history templates on recognized local routes, normalize more wire dialects, and keep title forks close to the live prefix. But declared LiteLLM exclusion, private-URL heuristics, larger output ceilings, parallel titles/summaries, and multi-attempt retry negotiation prevent a blanket 'OMP is always more cache stable' conclusion.
7. A model/config/plugin/permission change can legitimately alter system, tool, or template input. Fix request construction that changes accidentally; do not freeze changing user policy or keep unauthorized tools advertised as a cache optimization.

## Fixability and missing evidence

Client/config/plugin-addressable: accepted template kwargs and stable history-preservation contract; correct known-field mapping versus exact unknown wire extras; exact SDK/endpoint choice; accurate context/output metadata; title model/output/lifetime; measured header timeout; targeted retries/admission handling; backend-native affinity header spelling.

Backend-only or needs backend participation: whether APC is enabled, request-to-replica routing, template behavior, cache salt, tool-template rendering, actual model alias resolution, preemption/eviction, upstream abort propagation, and allocator/scheduler limits. A deterministic client payload is necessary for token reuse but does not guarantee those conditions.

No production request capture or live tokenization was available, so this audit cannot rank these conditional mechanisms as the actual on-prem cause. The useful discriminators are the final OC/OMP wire bodies and resolved model/replica, the exact rendered input token IDs across two successive tool turns (including assistant reasoning), title/compaction concurrency, timing/retry/cancel traces, and server-side prefix-cache/preemption metrics. No such observations were fabricated.
