# OpenCode 1.19.4 versus OMP: cache-loss assessment

## Scope

The audit covers the complete **custom OpenAI-compatible request path**, from stored conversation and live tool/prompt inputs to the pinned SDK wire format, auxiliary requests, retries and response replay. It does not claim a line-by-line audit of unrelated native Anthropic/Gemini transports, nor observation of the private LiteLLM/vLLM deployment.

- OpenCode: `148842ef7cb1bc34192b3fff57d0f9721ab9c801` (`v1.19.4`).
- OMP: `6f3fbc94c567c0ac619c013dd15d718356eecba1`.
- OpenCode default AI SDK: `ai@6.0.168`, `@ai-sdk/openai-compatible@2.0.41`.
- Full source inventories and line references: [system/tools](analysis/prompt-tools.md), [history/replay](analysis/history.md), [transport/pressure](analysis/transport.md). These are analysis artifacts; their fixability descriptions characterize upstream, not an inventory of this plugin's later fixes.

The current implementation additionally covers request-correlated usage anchors, same-host cross-process admission, an explicit GLM plaintext-reasoning profile, durable reconstruction checkpoints and compact generated skill catalogs. See [README.md](README.md) for defaults, deployment options and final verification. Native MCP Code Mode is reused rather than reimplemented.

For the suspected GLM 5.3 NVFP4 deployment, the [public NVIDIA template](https://huggingface.co/nvidia/GLM-5.3-NVFP4/blob/main/chat_template.jinja) renders reasoning effort at the very beginning (default `max`) and defaults `clear_thinking` to false. Changing effort or stripping historical reasoning can change prefixes, but neither behavior is established on the private server. NVFP4 weights/activations do not establish the KV dtype, serving engine or deployed context limit. The explicit GLM profile preserves request overrides and does not apply Qwen options.

## Findings ranked by relevance

| Mechanism | What differs from OMP | When it matters | Response |
| --- | --- | --- | --- |
| Early live system instructions | OC rereads local and URL instructions each model step. OMP normally snapshots/rebuilds base context at explicit boundaries. URL failures in OC produce an empty contribution. | A changing file, nondeterministic URL, intermittent fetch failure or per-user system replacement changes an early prefix. | Keep live policy authoritative. Use a stable local instruction source; diagnose system changes rather than freezing the first successful policy forever. |
| Transient mode reminders | OC's default plan/build reminder is attached only to the latest in-memory user message. It disappears from the old turn when a new user turn arrives. | New user turns in affected modes, not every unchanged tool iteration. Experimental plan transitions are persisted and are a counterexample. | Plugin retains recognized historical reminders without reviving old mode instructions on the current turn. |
| Historical thinking in Qwen templates | OMP can emit `chat_template_kwargs.preserve_thinking=true` so old thinking remains rendered. OC does not automatically select this local-template policy. | Affected Qwen template defaults; keeping `reasoning_content` in JSON alone is insufficient if the template strips it. | Configure the known template's history-preservation option. Do not enable unknown template flags for every model. **Declared LiteLLM is excluded from OMP's automatic local-thinking detection**, so the advantage is configuration-dependent. |
| Mode option camelization | OC's experimental mode expansion camel-cases arbitrary wire fields; compatible SDK only translates a small recognized set back. | Modes containing `chat_template_kwargs`, `enable_thinking`, `prompt_cache_key`, or output-limit fields. Ordinary model options follow a different path. | Plugin restores the known compatible wire names, preserving explicit wire values and tenant salt. |
| Full direct MCP schemas | OC normally presents all visible MCP tools directly. OMP can use compact `xd://` catalogs with on-demand schemas. | Many/large schemas, reconnects, `tools/list_changed`, changed resource capabilities. This increases both fixed size and the size of a prefix affected by catalog changes. | Canonicalize object ordering, retain current semantics. Consider OC's existing experimental codemode when appropriate; do not advertise disconnected/revoked tools to keep a cache hit. |
| Installed definition/system hooks | OC invokes `tool.definition` every iteration. OMP snapshots selected skill/eval/model-agent presentation inputs and announces some updates in history. | A plugin injects clocks, counters, live state or changing description/schema prose. No default OC hook was shown to do this. | Make the specific plugin deterministic. Final wire diagnostics identify changed tools/system; no blanket freeze. |
| Late native compaction trigger | OC compares prior completed usage before the next call and again after step completion. Pending user input and a newly large tool result are not fully preflight-tokenized. | A large new addition crosses the actual served limit between checks. | OMP-inspired pre-dispatch budgeting must count the final messages, tools and format overhead, then reuse a rolling summary and retain recent complete protocol groups. |
| Native compaction request shape | OC serializes the selected old history into a new summarization prompt; large tool results are truncated in that serializer. OMP local summaries also use separate serialized context, but have bounded folding and summary reuse. OMP handoff is a different, live-prefix-preserving path. | Large old histories and repeated compaction. A compaction request can itself overflow. | Bound every internal summary request; fold only uncovered history through the previous summary. Compaction changes a prefix deliberately, so use a recovery band rather than tiny per-step rewrites. |
| Title request pressure | OC may fall back to the main model, with unrelated title instructions and the ordinary output ceiling, in parallel with the main request. OMP titles also run concurrently, but fork the live prefix and use a short deadline. | Same physical GPU/cache and insufficient concurrency headroom. | Native `agent.title.disable: true` eliminates the request. Otherwise the plugin holds one endpoint admission lease through stream completion. |
| Slow-prefill cancellation | OC has a default 300-second header timeout. OMP disables its first-event deadline for recognized local-serving URLs, including private LiteLLM URLs. | Slow cold prefill or long endpoint queues. Repeated abort/retry can waste work and evict useful cache. | Configure `provider.options.headerTimeout` for the actual deployment; `false` disables that header deadline. Preserve explicit cancellation and suitable stream/absolute deadlines. |
| Retry after partial output | OC's outer processor retry policy is not OMP's provider-level pre-output commit gate. Partial-output/error filtering can change replay. | A transport fails after content/tool data starts. OMP also has its own recovery transformations and retries. | Preserve errors and cancellation; do not conceal the failure or automatically replay tools in a fetch wrapper. Core transactional retry policy cannot be safely replaced by a response-text hack. |
| Enabled old-output pruning | OC can replace deep historical tool outputs without OMP's warm-prefix suffix/idle guard. | **Only when explicitly enabled**; OC 1.19.4 defaults to false. | Keep native pruning disabled for stable wire history. Do not disable necessary context compaction as a substitute. |
| Reasoning representation aliases | OC's compatible parser handles `reasoning_content` and `reasoning`; OMP accepts additional provider shapes and signed block representations. | A particular proxy/model uses an unsupported alias/block representation. Ordinary nonempty reasoning already round-trips in OC. | Use the served API's canonical fields; a provider-specific adapter may be needed. Do not invent or strip signed thinking data. |
| Error/empty-message/media normalization | Both clients transform stored content. OMP has broader repair and multimodal handling; OC's converter may drop some errored turns or unsupported media and fetch non-data attachment URLs. | Failures, model switches, mutable/expiring media URLs and unsupported formats. | Preserve valid retained protocol groups. A fresh random internal part ID does not by itself imply a fresh wire token. Do not normalize away meaningful content for a hit. |
| Agent, permission, format and model changes | Both clients change prompt/tool shape for real capability or output-contract changes. OC JSON-output mode adds a schema tool and system instruction. | Explicit user/model/variant/mode changes, permission revocations, schema changes. | Necessary cache misses. Freezing these inputs is incorrect. |
| Replica/model/cache namespace | Existing affinity headers differ, but neither header existence nor a body key guarantees sticky routing. | LiteLLM selects another deployment/pod, retries/failover changes placement, or model/LoRA/salt changes. | Server routing/APC configuration is required; preserve isolation. The plugin supplies explicit session metadata, not a fictional guaranteed cache hit. |

## What is not established as a cause

- **"Every full-history request clears the cache."** False. A stateless Chat Completions request resends context; vLLM can reuse identical rendered prefix blocks. Wire bytes and GPU prefill work are different measurements. Rolling summaries reduce wire context after thresholds, not by omitting unrepresented history.
- **"OpenCode always sends tools in random order."** False for 1.19.4. Final tool names, task agents, skills, references and MCP instructions are sorted. Nested schema property-order changes and actual catalog changes are separate issues.
- **"The timestamp changes every request."** The generated environment contains a calendar date, not a seconds-level clock. It changes at a day boundary. The plugin removes it entirely.
- **"All skills are reread each iteration."** The 1.19.4 skill catalog is instance-cached. Its formatted text is rebuilt, but unchanged data stays deterministic.
- **"OpenCode drops all thinking."** False for ordinary nonempty `reasoning_content` on the pinned compatible path. Parser aliases, model-switch conversion and server-template removal are more specific possibilities.
- **"New synthetic message IDs change the rendered prompt."** The inspected internal IDs do not survive the compatible wire converter as message text. Tool call IDs, actual result paths and content are different fields.
- **"OMP always freezes the whole prompt."** False. Its implicit prefix binding depends on model policy, it has many live tool-description getters, and context/payload extensions can rewrite inputs. It also performs pruning, speculative/parallel summary paths and other auxiliary requests.
- **"No cache hint means APC is off."** False. vLLM APC hashes token blocks. A body key can influence a supporting proxy/provider, but is not the APC on/off switch.
- **"The UI says zero cached tokens, so the cache was missed."** Not proven. Usage aliases unsupported by the SDK can appear as zero. Verify server counters or canonical `prompt_tokens_details.cached_tokens` for the actual version.
- **"A long maximum completion reserves all those KV tokens immediately."** Not a general vLLM allocation rule. A cap limits potential future generation, not necessarily an up-front full reservation.

## Native hook limitation

Calling `client.session.summarize()` inside a generation hook can deadlock: the handler enqueues compaction and awaits `promptSvc.loop()`, while an already-running runner waits for the existing loop, which is itself waiting for the plugin hook. The earlier `chat.message` hook runs before the pending message is persisted. Therefore an OMP-style preflight implementation must either own idle-session scheduling outside those hooks or compact outgoing requests independently. This plugin uses the latter and leaves the OpenCode transcript untouched.

## Evidence versus production attribution

The source establishes mechanisms and differences. Local verification can prove request shape, stable prefixes, concurrency limits, cancellation, token-estimator budgets, summary reuse and correct error propagation. It cannot prove the private server's tokenizer, rendered template, actual GPU KV occupancy, replica choice or semantic summary quality.

The exact `kv cache capacity exhausted` message was not conclusively located in the deployed server because that server/version is unavailable. Capacity exhaustion is not identical to a prefix miss. See the official [vLLM prefix-cache design](https://docs.vllm.ai/en/stable/design/prefix_caching/), [preemption guide](https://docs.vllm.ai/en/stable/configuration/optimization/#preemption), and [LiteLLM cache-aware routing](https://docs.litellm.ai/docs/proxy/cache_aware_routing). Their current behavior must not be assumed for an unspecified older deployment.
